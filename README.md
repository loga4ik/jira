# Jira-клон — трекер задач для команд

[![CI](https://github.com/loga4ik/jira/actions/workflows/ci.yml/badge.svg)](https://github.com/loga4ik/jira/actions/workflows/ci.yml)

Веб-приложение для ведения проектов: задачи и подзадачи со статусами, команда проекта и чат в реальном времени. Фронтенд — этот репозиторий, бэкенд — [loga4ik/jira_back](https://github.com/loga4ik/jira_back).

## Возможности

- **Регистрация и вход** — JWT с ротацией refresh-токенов, сессия переживает перезагрузку страницы.
- **Проекты** — создание, редактирование, удаление; у каждого проекта свой адрес (`/project/5`), им можно поделиться. Проект можно отметить главным — после входа откроется сразу он.
- **Роли** — владелец управляет проектом и командой, участники работают с задачами. Посторонний проект не увидит, даже зная ссылку.
- **Задачи и подзадачи** — статусы «новый», «в работе», «завершён», исполнитель из команды.
- **Команда** — добавление и удаление участников проекта.
- **Чат проекта** — WebSocket, сообщения видят только участники.
- **Светлая и тёмная тема.**

## Авторизация

```
Вход ──► access-токен (JWT, 15 мин) в теле ответа ──► хранится в памяти вкладки
     └─► refresh-токен (7 дней) в httpOnly-куке   ──► JS к нему доступа не имеет
```

- **Access-токен хранится только в памяти** — не в `localStorage`, где его прочитал бы любой скрипт при XSS. После перезагрузки страницы он восстанавливается по refresh-куке.
- **Access — stateless, refresh — stateful.** Access проверяется по подписи без похода в базу, поэтому он короткий. Refresh хранится в базе в виде SHA-256-хеша, поэтому его можно отозвать.
- **Ротация с обнаружением кражи.** Каждый refresh одноразовый: при обмене выдаётся новый. Повторное предъявление уже использованного токена означает, что он утёк, и гасится вся цепочка сессии. Короткое окно (10 с) прощает одновременное обновление из двух вкладок.
- **Автоматическое обновление на клиенте** (`src/Lib/api/baseQuery.ts`): запрос получил 401 → токен обновляется → запрос повторяется. Если 401 пришли сразу на несколько запросов, обновление всё равно одно — все ждут общий промис (`src/Lib/api/authToken.ts`).
- **WebSocket**: токен проверяется при рукопожатии, войти в комнату чата может только участник проекта, автор сообщения берётся из токена, а не от клиента.

## Работа с данными

Все запросы к API идут через RTK Query: один `createApi` на приложение (`src/Lib/api/api.ts`), эндпоинты подключаются в `userApi.ts` и `projectApi.ts`. Своих слайсов для серверных данных нет — в Redux лежит только кэш RTK Query.

- **Компонент сам берёт, что ему нужно.** Команду проекта показывают пять компонентов в разных частях дерева — каждый вызывает `useGetTeamQuery(projectId)`, а запрос уходит один. Пропсы через несколько уровней не нужны.
- **Кэш на каждый проект отдельно.** При переходе из проекта в проект данные прошлого не мелькают, сбрасывать стор вручную не нужно.
- **Теги вместо ручного обновления.** Мутация объявляет, что изменилось, и подписанные данные перезапрашиваются сами:

| Действие | Что перезапросится |
|---|---|
| создать или удалить проект | список проектов на главной |
| отредактировать проект | проект, его задачи и список на главной |
| отредактировать задачу | задачи проекта |
| добавить участника | команда и список «кого можно добавить» |
| удалить участника | команда и задачи (с подзадач снимается исполнитель) |

- **Точечное обновление там, где перезапрос лишний.** Смена статуса или исполнителя подзадачи не перезагружает все задачи: подзадача заменяется прямо в кэше (`updateQueryData`).
- **Ошибка — не данные.** Если сервер отказал, кэш не трогается, форма остаётся открытой и показывает причину.
- **Выход стирает весь кэш** — следующий вошедший на этом компьютере не увидит чужих проектов.
- При возврате на вкладку данные обновляются сами — задачи могли поменять другие участники.

## Права доступа

Проверяются на сервере, интерфейс только подстраивается под них.

- Express-middleware `requireProjectMember` / `requireProjectOwner` на всех маршрутах проектов, задач, подзадач и команды. Правило «участник = член команды или владелец» записано в одном месте (`services/access.js`).
- **Чтение и работа с задачами** — участник. **Редактирование проекта, команда, удаление** — только владелец.
- Посторонний получает `403`, несуществующий проект — `404`. Задачу или подзадачу из чужого проекта нельзя изменить через свой.
- На клиенте запрос проекта — он же проверка доступа: при `403`/`404` показывается «нет доступа», а задачи, команда и чат даже не запрашиваются. Кнопки управления видит только владелец.
- **Ссылка на проект для гостя:** `/project/5` → `/login?from=/project/5` → после входа обратно в проект. Параметр `from` принимает только внутренние пути — подменить его на чужой сайт нельзя (защита от open redirect).

## Тестирование

87 тестов: авторизация, формы, работа с данными и права доступа.

- **Сетевой слой**: обновление токена по 401, один `/refresh` на несколько одновременных запросов, поведение при истёкшей сессии.
- **RTK Query**: пользователь попадает в кэш после входа без лишнего запроса; выход очищает токен и кэш даже при ошибке сервера.
- **Кэш и теги**: после создания, удаления, правки проекта и изменения команды перезапрашивается ровно то, что нужно; при ошибке кэш не трогается; смена подзадачи не перезапрашивает задачи; выход очищает кэш.
- **Страница проекта**: данные из четырёх запросов собираются вместе, каждый общий запрос уходит один раз, посторонний видит «нет доступа» без лишних запросов.
- **Маршруты**: гость не видит защищённую страницу даже на мгновение и уходит на вход с адресом возврата; `?from=` ведёт обратно, внешние адреса отбрасываются.
- **Формы** (React Testing Library): ошибки валидации, ответы сервера (401, 409), блокировка кнопки во время запроса, нормализация телефона. Поля ищутся по подписи (`getByLabelText`), поэтому тесты заодно проверяют доступность.
- **MSW** вместо моков `fetch`: тест описывает правила поддельного сервера («пускаю только с новым токеном»), а не порядок ответов.
- Ключевые тесты проверены «мутациями»: если в коде убрать нужную строку (сброс тега, проверку адреса), тест падает.

```bash
npm test            # один прогон
npm run test:watch  # перезапуск при изменениях
npm run coverage    # покрытие, HTML-отчёт в coverage/
```

## CI

GitHub Actions на каждый push и pull request в `main`: `npm ci` → ESLint (без предупреждений) → проверка типов → тесты → сборка. Версия Node зафиксирована в `.nvmrc`, одна и та же локально и в CI.

## Производительность

Страницы загружаются лениво через `React.lazy` + `Suspense`: каждая страница — отдельный файл, который скачивается при первом переходе на неё. Пока он загружается, шапка остаётся на экране.

| | Начальный JS | gzip |
|---|---|---|
| Все страницы в одном бандле | 470 КБ | 151 КБ |
| С ленивой загрузкой страниц | **244 КБ** | **81 КБ** |

Валидация форм (zod, react-hook-form) теперь скачивается только на страницах входа и регистрации — вошедший пользователь её не загружает.

## Доступность

- В форме регистрации у полей есть подписи, связанные с инпутами; ошибка привязана к полю через `aria-describedby`, неверное поле помечено `aria-invalid`.
- Ошибка сервера объявляется скринридером сразу (`role="alert"`).
- У иконочных кнопок есть понятные названия («Показать пароль», «Включить тёмную тему»).

## Запуск локально

Нужны Node 24 (`nvm use` возьмёт версию из `.nvmrc`) и PostgreSQL.

**Бэкенд** ([jira_back](https://github.com/loga4ik/jira_back)):

```bash
git clone https://github.com/loga4ik/jira_back.git
cd jira_back
npm install
cp .env.example .env          # заполнить JWT_ACCESS_SECRET
# подключение к базе — db/config/database.json
npm run db-create
npm run db-migrate
npx sequelize db:seed:all     # статусы задач
npm run dev                   # http://localhost:4000
```

**Фронтенд:**

```bash
git clone https://github.com/loga4ik/jira.git
cd jira
npm install
npm run dev                   # http://localhost:5173
```

Dev-сервер Vite проксирует `/api` и `/ws` на бэкенд, поэтому CORS в разработке не нужен.

## Структура

```
src/
  features/auth/   схемы zod для форм, безопасный возврат после входа
  features/mainProject/  главный проект (localStorage)
  Hooks/           текущий пользователь, id проекта из адреса
  Lib/api/         RTK Query: общий api, userApi, projectApi, baseQuery с обновлением токена
  Lib/webSocket/   клиент чата
  types/           типы данных API
  UI/App/          роутинг
  UI/HOC/          Layout, ProtectedRoute, GuestRoute
  UI/Pages/        страницы: вход, регистрация, главная, проект
  UIKit/           общие компоненты: поля, кнопки, модалки
  test/            окружение тестов, MSW-сервер, хелперы рендера
```
